## Canonical finding dispositions

### `csf_0d909583e66f0b8ee56eb25d` — output-directory rebinding

Occurrence: `occ_e95d4bc381d2b6d694e45d66`
Candidate: `core-split-output-directory-rebind`
Sealed location: `crates/cakesplitter-core/src/resumable.rs:201`

Root cause: the selected destination was reduced to a pathname and a stored
directory fingerprint. The directory handle used to obtain that fingerprint
was dropped before later Slice and Manifest publication.

Remediation:

- A destination guard now opens the output directory and every replaceable
  ancestor for the full resumable Split or Merge operation.
- On Windows, those handles intentionally omit delete sharing, so the guarded
  objects cannot be renamed, deleted, junctioned, or replaced while the task
  publishes output.
- The guard records volume and native file index and revalidates the retained
  handle, path-resolved identity, directory kind, and no-reparse chain before
  creation, after externally observable checkpoints, before and after each
  atomic publication, and before returning success.
- Restart and resume reacquire the destination and compare it with the persisted
  fingerprint. A mismatch or an identity that cannot be proven returns
  `destination_identity_changed`.
- A detected mismatch stops publication. No final Manifest is created. Partial
  data is left incomplete rather than deleted through a potentially rebound
  pathname; cleanup remains identity-checked.
- Privacy-safe Desktop error mapping does not expose the destination path.

The unchanged sealed proof previously produced four package entries in the
replacement directory, zero entries in the originally selected directory, and
reported Split success. After remediation, its unchanged rename statement
fails with Windows error 32 because CakeSplitter retains non-delete-sharing
authority over the selected directory. The harness then aborts at its own
`unwrap`; it cannot reach the old success assertions. Independent equivalent
tests handle the denied rename and confirm no replacement entry and no final
Manifest.

### `csf_b5af83ca015047cc45df601b` — unbounded task admission

Occurrence: `occ_a64a7219d1de01727d13a4e0`
Candidate: `runtime-task-admission-002`
Sealed location: `crates/cakesplitter-desktop-runtime/src/engine.rs:449`

Root cause: allowed enqueue commands persisted tasks and fed an unbounded Rust
channel without an atomic aggregate nonterminal-task limit. Reusable selection
tokens could therefore grow native durable state without bound.

Remediation:

- All public command-path admissions are serialized by the native engine.
- The SQLite store performs an authoritative nonterminal count and insertion in
  one transaction. Terminal retry-to-queue transitions use the same atomic cap.
- The worker channel is a bounded `sync_channel`; only one native worker and one
  execution context can be active.
- Capacity is checked before path validation, disk-space probing, task
  persistence, channel insertion, or execution-context allocation.
- A failed channel insertion removes its newly queued admission before an error
  is returned.
- Startup counts nonterminal recovery rows before decoding or dispatching them,
  fails closed above the recovery cap, and prunes terminal history only.
- Metadata and Slice-plan limits are applied on admission and on persisted-row
  decoding. Excess requests return specific bounded IPC errors and are never
  silently dropped.

The explicit native limits are:

| Resource | Limit | Enforcement |
| --- | ---: | --- |
| Active native tasks | 1 | Single authoritative worker |
| Queued channel slots | 64 | Rust `sync_channel` |
| Persisted nonterminal tasks | 64 total, including active/recoverable tasks | SQLite transaction |
| Concurrent admission critical sections | 1 | Engine mutex |
| Retained terminal-history tasks | 500 | Terminal-only SQL pruning |
| Task metadata | 32 MiB per checksummed JSON record | Before persistence and before decode |
| Task-plan Slice count | 50,000 | Shared Cake Package bound plus store validation |
| Bootstrap recovery records | 64 nonterminal tasks | Count before recovery/list dispatch |
| Quarantine records | 20 | Existing bounded quarantine policy |

The 32 MiB record limit accommodates a legitimate 50,000-Slice resumable
checkpoint while still bounding each durable object. Aggregate nonterminal
state is bounded independently by the 64-task cap.

### `csf_30bcb95354573088f53fcf09` — selection-identity rebinding

Occurrence: `occ_15072f006c9746c9329e4fac`
Candidate: `tauri-001`
Sealed location: `apps/desktop/src-tauri/src/selection.rs:45`

Root cause: opaque tokens retained path, expected kind, and issuance time but no
selection-time identity. Token resolution therefore authorized whichever
same-kind object occupied the path later.

Remediation:

- File tokens retain native volume/file identity, byte length, and modification
  time from the selection-time file handle.
- Directory tokens retain native volume/file identity.
- Future output tokens retain the selected parent identity and require the
  intended child name to remain absent; access errors are not treated as
  absence.
- Multi-Slice tokens retain parent identity, ordered path membership, and every
  Slice fingerprint. Hard-link aliases are rejected as duplicate identities.
- Every token resolution reopens and compares the current object before any path
  is returned. Missing, replaced, reparse, ambiguous, or inaccessible objects
  return `selection_identity_changed` and require explicit reselection.
- A failed resolution does not update the stored binding; restoring the original
  object makes the original token usable again while its TTL remains valid.
- Registry state is process-local, so an application restart never silently
  restores or rebinds an old selection token.

The remediation deliberately stops at the sealed selection-token boundary.
Durable Merge package binding is a separate sealed Low finding and remains
deferred as required by this task.

## Deferred Low findings and accepted limitations

The following four sealed Low findings remain unchanged and deferred:

1. `csf_6bfbe37d31cd74bb6b1e8bf2` — Windows in-place source mutation can produce a per-Slice-verified but unrebuildable package.
2. `csf_316f53e3dd0de1ce8867816d` — Durable Merge tasks are not bound to the package selected at enqueue time.
3. `csf_37799f0a8fc30ac823f952a7` — Package inspection can enumerate and persist unbounded physical entries.
4. `csf_3c9b706fc47cdc6eb3f0617b` — A rejected task snapshot can disable bootstrap listeners and Clear All recovery.

Accepted limitations for this checkpoint:

- The operation-lifetime rename/delete denial is a Windows-native guarantee.
  Other filesystem implementations receive identity and reparse revalidation,
  but v0.4 desktop security support must not claim equivalent semantics without
  platform-specific validation.
- Network, virtualized, removable, or unusual filesystems that cannot provide
  stable native identity may fail closed and require reselection.
- Identity rejection preserves owned incomplete data instead of following a
  changed path to delete it. Cleanup can therefore remain a manual, local action.
- Terminal history remains capped at 500 independently of the 64 nonterminal
  cap. The sealed bootstrap-parser Low finding is intentionally not changed here.
