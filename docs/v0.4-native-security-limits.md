# CakeSplitter v0.4 Native Security Limits

Status: v0.4.0 release limits, 2026-07-19

These limits apply to the native Rust/Tauri prototype. They are security and
reliability boundaries, not Cake Package format changes. Cake Package remains
format `1.0`; the existing manifest limits remain 16 MiB, JSON nesting depth
16, 50,000 Slices, and 200 UTF-8 bytes per portable filename.

## Package selection and binding

A durable Merge, Inspect, or Verify task stores package-binding version `1`.
The binding contains the parsed Manifest, exact Manifest-byte SHA-256, Manifest
native identity, package-directory native identity, ordered Slice filenames and
native identities, and a digest of the complete physical `.slice` membership.
The runtime compares that binding before work, during security-sensitive reads,
after streamed Merge input, and immediately before output publication. A changed
or ambiguous package returns `package_identity_changed`; the trusted binding is
not replaced.

On Windows, CakeSplitter retains non-delete-sharing handles for the package
directory and its replaceable ancestors, and for selected Manifest and Slice
objects while they are used. Reparse points, symlinks, junctions, inaccessible
objects, and filesystems that cannot prove stable identity fail closed.

## Package enumeration and inspection

| Resource | Limit | Result when exceeded |
| --- | ---: | --- |
| Physical entries inspected in one package directory | 65,536 | `package_enumeration_limit` |
| Physical `.slice` candidates | 51,024 | `package_enumeration_limit` |
| Unexpected `.slice` names retained for diagnostics | 1,024 | `package_enumeration_limit` |
| Entry filename length | 200 UTF-8 bytes | `package_enumeration_limit` |
| Aggregate enumeration metadata estimate | 24 MiB | `package_enumeration_limit` |
| Serialized native inspection summary | 24 MiB | `package_enumeration_limit` before task-result persistence |
| Unexpected diagnostics accepted by Desktop IPC | 1,024 | IPC validation failure |
| Diagnostic rows rendered per issue category | 20 | Remaining retained entries are not rendered |
| Recursion depth | 0 | Subdirectories are not traversed |
| Symlink, junction, or reparse traversal | 0 | Entry or path is rejected |

The candidate allowance is the 50,000-format maximum plus 1,024 bounded
unexpected diagnostics. Enumeration is streaming and stops at the first
exceeded limit. The Rust core owns these checks; UI truncation is presentation
defense only.

## Native task persistence and bootstrap

| Resource | Limit |
| --- | ---: |
| Active native execution contexts | 1 |
| Queued/nonterminal tasks | 64 total |
| Concurrent admission critical sections | 1 |
| Recovery candidates processed at startup | 64 nonterminal tasks |
| Retained terminal-history tasks | 500 |
| Task-list snapshots accepted or retained by the UI | 564 |
| Checksummed task metadata per row | 32 MiB |
| Task-plan Slice count | 50,000 |
| Quarantine diagnostic rows | 20 |
| Retained quarantined payload per row | 64 KiB |
| Retained quarantine reason per row | 1,000 UTF-8 bytes |

Task-state schema version `2` validates task IDs, schema and application
versions, checksums, status transitions, progress, plan limits, path shape,
package bindings, results, failures, and recovery checkpoints before execution.
Duplicate IDs are rejected by the SQLite primary key. Capacity is enforced
before persistence, file access, or worker allocation.

If more than 64 nonterminal rows are present at bootstrap, CakeSplitter keeps
only the allowed recovery set, retains at most 20 bounded diagnostic samples,
records the exact rejected count, and removes the remaining unsafe overflow
without materializing it. Terminal history is pruned to the newest 500 rows.
Corrupt rows are isolated individually. A future unsupported database schema is
renamed intact to a local `unsupported-v<version>` evidence file before a clean
current store is opened.

The UI exposes `ready`, `recovery-required`, `quarantined`,
`capacity-exceeded`, `unsupported-version`, and `corrupt` startup states.
Listeners are installed independently before the initial snapshot is loaded,
and a rejected snapshot cannot disable Clear All.

## Limitations

The strongest rename and replacement protection described above is currently
validated on Windows local filesystems. Network, virtualized, removable, or
unusual filesystems may not expose stable native identity and therefore may
require explicit reselection or fail closed. CakeSplitter does not claim that a
package remains immutable after the operation returns; later changes are
detected by Verify, Merge, or durable-binding revalidation.

Incomplete Split Slices can remain after a final integrity rejection, but no
Manifest completion marker is published. They are never represented as a
complete Cake Package and may require manual cleanup.
