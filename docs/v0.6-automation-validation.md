# CakeSplitter v0.6 Automation Validation

This is the bounded release-candidate validation record for application
version `0.6.0-dev`. It validates the CLI and Batch Job schema 1 workflows
against Cake Package format `1.0`; it is not a final-release report and does
not authorize a tag, remote, push, installer, or v0.7 work.

## Boundary and admission checks

The release binary was exercised from disposable directories outside the
repository. Boundary values were accepted and the first value above each
limit was rejected before operation execution:

| Input | Exact boundary | Above boundary | Observed result |
| --- | ---: | ---: | --- |
| Job specification | 8,388,608 bytes | 8,388,609 bytes | exit `0`; then exit `10`, `batch_spec_size_limit` |
| Operations | 1,000 | 1,001 | exit `0`; then exit `10`, `batch_operation_limit` |
| Dependencies/operation | 128 | 129 | exit `0`; then exit `10`, `batch_dependency_limit` |
| Dependency edges | 10,000 | 10,001 | exit `0`; then exit `10`, `batch_dependency_edge_limit` |
| Operation ID | 128 UTF-8 bytes | 129 UTF-8 bytes | exit `0`; then exit `2`, `batch_operation_id_limit` |
| Job name | 256 UTF-8 bytes | 257 UTF-8 bytes | exit `0`; then exit `2`, `batch_job_name_limit` |
| Metadata | 65,536 serialized bytes | above 65,536 | exit `0`; then exit `10`, `batch_metadata_limit` |
| JSON nesting | supported depth | 26 nested arrays | exit `10`, `batch_json_depth_limit` |
| JSON syntax | valid | truncated JSON | exit `2`, `batch_invalid_json` |

The exact 8 MiB and all other boundary checks produced no package, receipt, or
run-state output. Duplicate IDs, duplicate dependencies, unknown dependencies,
cycles, forbidden commands, and malformed operation shapes are covered by
`batch_rejects_cycles_duplicates_forbidden_commands_and_oversized_graphs`.

The documented limits are implemented in Rust before expensive planning or
filesystem access. The authoritative limits are also returned in machine
results and documented in `docs/batch-job-spec-v0.6.md`.

## Graph and policy validation

Three repeated validation passes for each fixture produced identical orders;
specification order wins ties:

| Fixture | Order |
| --- | --- |
| linear | `a,b,c` |
| fanout | `root,b,c` |
| fanin | `c,b,d` |
| disconnected | `z,a,y` |

Runtime failure policy coverage passed for both `stop` and
`continue-independent`. The production-path Rust tests show that a runtime
failure does not permit a dependent operation to run, while an independent
operation continues only under the independent policy. Preflight failures are
rejected before any operation is allocated; they do not become an implicit
continue policy.

## Endurance profile

A disposable release-binary profile ran 10 batch jobs containing 55 operations:
one batch Split plus nine mixed jobs (Merge, Inspect, and Verify), followed by
resume of every completed state. All 10 initial runs and all 9 applicable
resumes exited `0`; 18 rebuilt outputs were produced and byte-checked by the
workflow. Wall times for the ten runs were 89–267 ms. Persisted state sizes
were 1,806 bytes for the one-operation run and 13,894–13,908 bytes for the
six-operation runs. The profile removed its temporary directory after the
measurements; no orphan output remained.

The short profile did not sample OS-level peak memory or handle counts at a
useful resolution. Bounded Rust tests cover the relevant admission, diagnostic,
event, history, and queue limits, and the static review found no child-process
or network execution path.

Separate disposable fixtures covered a missing-package preflight failure, a
mutated-package integrity failure, and the two failure policies. The failed
operations remained terminal and no successful operation was silently admitted
under the `stop` policy.

## Cancellation, interruption, and resume

The production Rust tests cover cancellation before work, cancellation during
preflight, cancellation at a Slice boundary, pause/cancel wake-up, interrupted
state recovery, retry rules, and output-preserving resume. The batch unit test
`pre_cancelled_batch_persists_cancelled_state_and_one_terminal_jsonl_event`
confirms a persisted cancelled state and exactly one terminal event. Browser
smoke coverage also passed pause, resume, cancel, and reload-to-interrupted
flows.

The CLI has no synthetic cancellation flag; an external Ctrl+C injection was
not fabricated for this report. The tested cancellation token and abrupt-state
recovery paths are the supported deterministic harnesses. Exit code `130` is
reserved for cancellation and batch terminal failures use exit code `11`.

## JSON and JSONL

An independent PowerShell parser ran `batch validate`, `batch plan`, `batch
run`, `batch status`, and `batch resume` in JSONL mode. Every stream parsed as
JSON, had a stable top-level `runId`, matched `payload.runId` where present,
had monotonically increasing sequence numbers, exactly one terminal event, and
no event after terminal. Observed stream lengths were 2 (validate), 3 (plan),
2 (status), and 4 (resume); the run stream also passed the same assertions.

## Dry-run, privacy, and path safety

Top-level `plan`, `split --dry-run`, and `batch plan` were compared against a
before/after filesystem inventory and created no package, state, or receipt.
Receipt tests confirm that paths are masked and private values are not written.
Reparse-point, destination identity, source identity, and terminal-control
tests passed in the production Rust path. Batch paths are literal data: no
environment expansion, wildcard expansion, shell, executable, recursive batch,
HTTP, plugin, telemetry, cloud, or network path exists in the CLI capability.

## Compatibility

`npm run test:compatibility` passed Rust-to-Web and Web-to-Rust round trips and
rejected malicious manifest fixtures in both runtimes. Cake Package format
`1.0` remained unchanged.
