## Public API and schema stability

Cake Package 1.0 and its manifest validators are stable and should not change
for this audit. CLI schema 1 and Batch Job schema 1 are the intended public
contracts, but the batch machine contract is not internally consistent:

- Rust emits `command: "batch"`, top-level `runId`, and `batch-*`/
  `operation-*` JSONL events;
- the published CLI schemas omit `batch`, `runId`, and those event names;
- the TypeScript runtime validators reject the same actual batch shapes; and
- batch `not-ready` output is not allowed by the final-result status schema.

The documented additive-field rule also conflicts with strict unknown-field
rejection. CLI and Desktop receipts use different JSON shapes without separate
machine-readable schemas, and the final-result `result` and error `code` fields
are under-specified. Batch aliases, byte-vs-character limits, schema `$id`
policy, and deprecation rules need explicit documentation.

These are v0.8 publication blockers, not changes made in v0.7 audit mode.

## Security posture for v0.8

The current v0.6 security report, focused review, privacy model, and
Direct-Folder security explanation can be public after ordinary documentation
corrections. Historical remediation reports should be summarized or retained
privately because they expose internal scan identifiers and unnecessary exploit
reproduction detail. No raw scan artifact or PoC should enter the public tree.

The current reports correctly retain the accepted risks: unsigned local
preview, Windows filesystem variance, process-local batch admission, browser
memory limits, and Cake Package integrity without authenticity, encryption, or
signatures.

## Prioritized v0.7 backlog

### P0 — before any v0.8 publication work

- publish a correct batch CLI JSON/JSONL schema and matching TypeScript
  validators, including `batch`, `runId`, all batch event names, and
  `not-ready` semantics;
- decide author-email privacy and configure a verified public identity for new
  commits; and
- correct current-version documentation and explicitly classify historical
  security material.

### P1 — public-contract and attribution hardening

- add per-runtime receipt schemas and a complete stable error-code registry;
- resolve the additive-field/strict-validation contradiction and normalize
  schema identifiers;
- document batch aliases and byte-based limits;
- add npm license metadata or an explicit private-package rationale; and
- create a reviewed third-party inventory/NOTICE process.

### P2 — final publication evidence

- verify icon provenance and reproducibility;
- isolate or prune unreachable build residue in a controlled repository audit;
- create signed/verified v0.8 tags;
- perform a fresh-clone build, installer/checksum verification, final security
  scan, and public documentation review.

make an explicit author-email decision and keep private scan material out of
the public repository.
