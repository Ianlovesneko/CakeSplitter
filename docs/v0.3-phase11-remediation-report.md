## SEC-CS-001 — stable native Split source

Severity: Medium. CWE-367.

### Root cause

Split took a path metadata snapshot and detected length changes, early EOF, and
trailing data, but a same-sized in-place mutation could occur after a block was
read. The resulting package remained internally self-consistent while no longer
representing the selected source at return.

### Remediation

`split_file_with_progress` now:

1. opens the selected source once and records stable file identity, size,
   modification state, and Unix change time where available;
2. verifies that the selected path still resolves to that open object;
3. performs a complete preflight SHA-256 pass;
4. seeks the same handle back to the start and performs the normal streaming
   Split/hash pass;
5. requires both cryptographic reads and all identity/state checks to agree;
6. revalidates immediately before and after no-replace publication; and
7. rolls back only outputs whose recorded file identity proves they are owned
   by the current operation if a late source change is detected.

Instability returns the structured `source_changed` error. Final `.slice` and
`.cake.json` names are not left published. Files ending in `.partial` can remain
as explicitly incomplete evidence and are never reported as success.

### Regression and independent evidence

Six deterministic tests cover same-size in-place mutation, same-size path
replacement, truncation and restoration, final-Slice mutation, mutation before
finalization, and stable success. Every instability test also proves that no
final manifest or apparently valid final Slice remains.

Before remediation, the original harness returned success with unequal
package/source hashes. After remediation, the unchanged harness exits through
its vulnerable-success assertion because the real API returns `SourceChanged`.
All 17 core tests, including stable round trips and native no-replace races,
pass.

## SEC-CS-002 — trusted application shell

Severity: Medium. CWE-349.

### Root cause

The service worker promoted any successful same-origin navigation response into
the trusted `/index.html` cache key. A navigation to the Web Manifest could
therefore replace the offline application shell with JSON.

### Remediation

The service worker now has an explicit cache contract:

- `/index.html` is the sole offline shell key;
- only canonical `/` or `/index.html` navigations without a query can refresh
  that key;
- a shell response must be successful, non-opaque, non-redirected, same-origin
  canonical HTML containing the CakeSplitter application marker;
- alternate pages, unmarked HTML, redirects, opaque responses, and non-HTML
  resources cannot become the shell;
- static caching is limited to declared shell resources and flat hashed assets;
- cache lookup is restricted to the current versioned CakeSplitter cache;
- activation removes only obsolete CakeSplitter-owned caches; and
- selected files, Slices, manifests being processed, and task data are never
  service-worker cache candidates.

Service-worker activation remains explicit and is rejected while file
processing is active.

### Regression and independent evidence

Six VM tests execute the checked-in service worker and cover canonical shell
refresh, alternate navigation, redirects, unmarked HTML, canonical offline
fallback, and ownership-scoped cache cleanup. Two PWA controller tests cover
safe update activation during active processing.

The unchanged original poisoning probe now observes no cache writes (`[]`)
instead of manifest JSON under `/index.html`. Production Edge successfully
loads the trusted shell offline, performs a local Split, and confirms that no
selected filename, Slice, Cake Manifest, request body, or task data enters the
network or Cache Storage.

## SEC-CS-004 — Clear All persistence barrier

Severity: Low. CWE-362.

### Root cause

Main-thread persistence was serialized with other saves but not with Clear All.
A queued or late task save could recreate the removed `cakesplitter-tasks`
directory and metadata after the UI reported successful cleanup. Read-only
listing also created the directory unnecessarily.

### Remediation

`TaskStore` now owns one serialized operation queue, a monotonically advancing
generation, and a coalesced Clear All operation. Clear All advances the
generation synchronously before waiting, which permanently rejects old task
tokens. Saves check their token before queuing, before writing, and after the
write; a write invalidated while closing is discarded before the clear barrier
finishes. Reads and discards no longer create a missing OPFS directory.

The UI now:

- prevents new task admission while cleanup is running or after a failed
  barrier until reload;
- marks the active context as clearing before yielding;
- sends structured Worker cancellation and waits for terminal acknowledgement;
- waits for the TaskStore clear operation and every queued persistence promise;
- ignores stale Worker messages from the invalidated generation;
- reports success only after Worker, persistence, deletion, and UI-state
  barriers complete; and
- permits new tasks to capture and persist only the post-clear generation.

Concurrent cleanup requests share one deletion promise and the Clear All button
is disabled while the barrier is active.

### Regression and independent evidence

TaskStore tests use an OPFS-compatible in-memory implementation and cover active
Split and Merge metadata, a delayed writable close, a save invoked during
clearing, a stale post-clear save, concurrent clear requests, reload, an empty
OPFS root, and successful new-generation persistence.

A production Edge test uses real OPFS and the real App/TaskStore boundary. It
clears active Split and Merge tasks, receives a cancellation acknowledgement,
delivers a deliberately stale progress message, verifies the task directory
remains absent, reloads to an empty task list, and proves a new task can persist
before the second clear. This closes the original metadata-resurrection
condition.

## SEC-CS-003 — terminal-safe Unicode

Severity: Low. CWE-451.

### Root cause

The CLI escaped Rust control characters only on the common error sink. Success
paths printed `Path::display()` directly, and Unicode bidirectional formatting
characters are not classified by `char::is_control()`.

### Remediation

Human-readable CLI output now visibly escapes the complete Unicode
`Bidi_Control` set, including U+061C, U+200E-U+200F, U+202A-U+202E, and
U+2066-U+2069, using notation such as `\u{202e}`. Existing ASCII/C0/C1 escaping
remains in force. Split and Merge success paths, core errors, and Clap parse
errors all pass through terminal-safe rendering. Safe ordinary Unicode remains
readable.

Inspect remains valid machine-readable JSON. Its serialized JSON uses standard
JSON escapes such as `\u202e`, so a parser recovers the original filename while
the terminal never receives a raw bidi control. Verify success contains only a
validated numeric count; Verify errors use the common safe error sink. The CLI
has no task-name or warning output mode to remediate.

### Regression and independent evidence

Captured-process tests cover every required bidi control plus the other Unicode
`Bidi_Control` characters, a disguised extension, bidi combined with ANSI ESC,
safe Unicode, Split, Merge, Inspect JSON parsing, Verify success, and Verify
failure on a missing bidi-named Slice.

Before remediation, the real CLI emitted raw U+202E. The independent after-fix
probe exits successfully, contains no raw U+202E, contains `\u{202e}`, and
confirms the real filesystem output names still preserve the original Unicode
character.

## Focused review and remaining limitations

The final review found no cosmetic-only fix, unsafe fallback, weakened parser,
format change, remote processing, telemetry, or new Critical/High issue.

Accepted limitations remain:

- native stability is a fail-closed multi-pass/identity protocol, not a claim
  that ordinary filesystems provide immutable snapshots or prevent changes
  after the final check;
- service-worker shell identity assumes the same-origin application server is
  not already compromised;
- the Clear All generation coordinates one running App/TaskStore context.
  Concurrent trusted-tab metadata behavior remains the separately rejected,
  bounded local-hardening case from the sealed scan and is not authoritative
  file content;
- `cargo-audit` was unavailable in this execution environment. No new crate
  version entered the lockfile; the only Rust dependency change is a test-only
  reference to the already locked `tempfile` crate.
